做后台管理系统，最浪费时间的环节不是写业务，是**搭底座**。

权限怎么设计？菜单和按钮怎么控制？令牌怎么刷新？审计日志记什么？每次开一个新后台，这些问题都要重新回答一遍。回答得不好，三个月后就会发现：删个用户没人知道是谁删的，某个接口谁都能调，退出登录后 token 还能用。

这些问题不新鲜，解决方案也很成熟。它们只是**每次都要被重新实现一遍**。

<!--more-->

## 克隆下来就能跑

Chet.Admin 的定位是：把上述所有问题提前解决掉，形成一个可以直接用的企业级后台。

- 后端：.NET 10 + Clean Architecture，C# 12
- 前端：Vue 3 + Vben Admin（Monorepo）
- 数据库：EF Core
- 缓存：Redis
- 部署：Docker Compose 编排后端、Redis、Nginx

启动流程简单到有点不真实：

```bash
dotnet run   # 后端，Swagger 和种子数据自动初始化
pnpm dev     # 前端，秒级热更新
```

启动后就能登录，不用先写一堆初始数据。

## 权限：三层防护，不是三道摆设

RBAC 最容易做歪的地方，是只做了"菜单可见"，没做"接口可控"。

Chet.Admin 的权限模型分了三层：

- **菜单级**：没有权限的菜单，前端不渲染
- **按钮级**：没有权限的操作按钮，点不动
- **数据级**：五种数据权限范围，决定你能看到哪些部门、哪些人的数据

三层是联动的。菜单藏起来不等于接口安全，所以后端每个接口都要过授权。这一点听起来是常识，但很多后台项目的接口其实是裸奔的。

## 认证：双令牌是基本操作

- **Access Token**：默认 30 分钟，短期有效
- **Refresh Token**：默认 7 天，用来换新令牌

此外还内置了 BCrypt 密码哈希、限流防护、验证码、登录失败锁定、密码过期策略。

这些东西单独看都很基础，但组合起来才是一套能扛住真实攻击面的认证体系。

## 可观测性与审计

- **Serilog 结构化日志**：请求、异常、业务日志分开
- **操作审计**：谁在什么时候做了什么，记录在案
- **在线用户追踪**：当前谁在线，一目了然
- **通知公告**：系统内部的消息模块

审计这个功能，平时没人看，出事的时候是唯一的证据链。等需要的时候再补，历史数据已经没了。

## 接口版本化

`/api/v1` 不是装饰。项目支持 URL、Header、Query 三种版本识别方式，多版本可以平滑并存。老客户端继续用 v1，新功能上 v2，互不干扰。

## 前端也不是将就的

基于 Vben Admin 和 Ant Design Vue，浅色 / 深色主题跟随系统切换。13 个核心功能模块已经把常见的后台场景铺好了，加业务页面时基本是"填空"而不是"从零搭"。
